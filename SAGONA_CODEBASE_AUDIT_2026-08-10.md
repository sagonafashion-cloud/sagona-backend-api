# SAGONA CODEBASE AUDIT — 2026-08-10

Scope: full codebase (`backend/`, `frontend/`, `sagona-app/` mobile) reviewed by 5 parallel read-only agents — (A) auth/middleware/config, (B) mobile app, (C) payments/orders/delivery/GST, (D) products/admin/bulk-upload/analytics/support/chat/try-on/sizing, (E) frontend web. Findings below are reconciled and deduplicated across slices where the same issue was flagged from multiple angles.

## EXECUTIVE SUMMARY

SAGONA's codebase shows a generally security-conscious backend (consistent bcrypt/JWT hygiene, global NoSQL-injection defenses, mostly-correct IDOR scoping, magic-byte file validation, HMAC-verified Razorpay signatures) undermined by two live, exploitable gaps that need immediate attention. First, `POST /api/payment/verify` (`backend/controllers/paymentController.js`) marks any of a user's own pending orders as "paid" after verifying a genuine Razorpay signature for a *different, cheaper* payment — a real user can pay ₹10 for one item and use that receipt to mark a ₹50,000 order as paid, and the same payment can be replayed across multiple orders. Second, `frontend/cart.html` renders product name/colour/image with unescaped template-literal `innerHTML`, unlike every other cart renderer in the codebase — a compromised or careless bulk product upload (an explicitly untrusted data source per the code's own comments) becomes stored XSS on the site's highest-traffic pre-checkout page.

Beyond those two, the audit surfaced a cluster of HIGH-severity gaps worth fixing this sprint: admin login has no account-level lockout (IP-only rate limiting is bypassable via proxy rotation, and the seeded `super_admin` account has no forced 2FA); the Cloudinary upload/delete routes are missing the `requireRole` check every sibling admin route has, letting a low-privilege `viewer` admin delete live product images; order creation and stock reservation are not wrapped in a transaction, causing both permanent stock leaks on partial failure and unlimited oversell for any product without size/colour variants; the AI chat tool builds MongoDB `$regex` queries from unescaped, unauthenticated user input (a hardened, escaped version of the same search already exists elsewhere in the codebase, it just isn't reused here); and the customer-facing Returns page is a non-functional stub that tells users their return succeeded when nothing was submitted.

The MEDIUM/LOW tier is dominated by consistency problems rather than new vulnerabilities: escaping is applied correctly in most places but inconsistently in others (admin.js, account.js, tryOn.js, sizing.js each have one or two unescaped interpolation sites alongside otherwise-correct code); there are at least three independent cart renderers, six independent auth-header implementations, and two independent password-reset flows, all capable of drifting out of sync; and several silent `catch {}` blocks leave users with no feedback on failure. None of these are exploitable on their own, but they represent real maintenance risk and a couple (admin.js modals, sizing.js child-profile names) are stored-XSS vectors that should be fixed alongside the cart.html CRITICAL using the same `escapeHtml()` helper that's already imported in most of these files.

**Verification caveat:** `npm audit` could not be run against any of the three `package.json` files — the sandbox's bash tool returned RPC/mount errors throughout this audit. Dependency CVE exposure is therefore unverified and should be checked separately (see Open Questions).

## DUPLICATE / DEAD / CONFLICTING CODE

- **Three independent cart renderers**: `frontend/cart.html` (inline, unescaped — Finding 2), `frontend/nc_assets/js/cart.js` (escaped, used by other pages), and drawer-cart logic in `drawer.js`. All three read the same localStorage cart shape but maintain separate rendering logic that can drift.
- **Two independent password-reset flows**: customer (`authController.js` + `reset-password.html`) and admin (`adminAuthController.js`), each with its own OTP/token generation and validation logic instead of a shared helper.
- **Six+ independent auth-header/token-attachment implementations** across frontend scripts (`api.js`, `admin.js`, `account.js`, `checkout.js`, `chatbot.js`, and the mobile `api.ts`) instead of one shared authenticated-fetch wrapper — the root cause of Findings 28 and 48's inconsistent 401 handling.
- **Two `sanitizeUrl()` implementations** (Finding 46) — `config.js`'s shared version and at least one local reimplementation.
- **Two regex-search implementations for product lookup**: the hardened, escaped `escapeRegex()`-based version in `productController.js`, and the unhardened direct-`$regex` versions in `chatController.js` (Finding 8) and `orderController.js`'s admin search (Finding 16) that don't reuse it.
- **`returns.html` is effectively dead/fake code** (Finding 9) — it duplicates functionality that already exists and works correctly in `account.js`'s `submitReturnRequest()`, but doesn't call it.
- **Bulk-upload preview vs. commit logic diverges** (Finding 17) — `validateProduct()` and the efficient `$in`-based existence check (Finding 18) both exist and work correctly at preview time, but the commit step reimplements a weaker, less efficient path instead of reusing them.
- **Order status-transition rules duplicated** between the generic admin order route and the delivery-specific controller (Finding 38), maintained independently.
- **Rate limiter configs duplicated** (Finding 32) instead of built from one factory function.

## CONFIRMED WORKING

- **Password hashing**: customer and admin passwords are hashed with bcrypt before storage; no plaintext password handling found anywhere in the reviewed code.
- **Customer account lockout**: `authController.js:85-121` correctly implements per-account `loginAttempts`/`lockUntil` after repeated failures — the pattern Finding 3 recommends extending to admin accounts.
- **JWT algorithm pinning**: nearly all `jwt.verify` call sites correctly restrict to `{algorithms:['HS256']}`, preventing algorithm-confusion attacks (the one exception is Finding 14).
- **NoSQL injection defense**: `express-mongo-sanitize` and `hpp` are wired globally in `server.js`, providing baseline protection against MongoDB operator injection across all routes.
- **File upload validation**: upload handling validates file content by magic bytes, not just declared MIME type/extension, closing a common file-upload bypass.
- **Razorpay signature verification, done correctly in two places**: both `createOrder`'s payment-intent flow and the separate webhook handler verify HMAC signatures using `crypto.timingSafeEqual` (constant-time comparison), and both correctly derive the amount from the server-side order record rather than trusting client input. **This is the pattern Finding 1's fix should copy** — `verifyPayment` is the one payment code path that doesn't follow it.
- **Server-side price/GST recomputation on order creation**: `computeOrderTotals`-equivalent logic in `orderController.js` always re-derives price, tax, and grand total from the database product/store records at order-creation time, never trusting client-submitted prices. **This directly resolves the mobile slice's flagged concern about client-supplied checkout prices (COD orders included)** — the price a mobile client sends is not the price that gets charged; the backend recomputes it. The one still-open question in the same family is Finding 27 (the `discount` field specifically), which is narrower and unconfirmed rather than a repeat of the same class of bug.
- **IDOR scoping**: customer-facing order/profile/wishlist endpoints consistently scope queries to `req.user.id`/`req.user._id`, preventing one customer from reading another's orders by guessing IDs.
- **Variant-product stock decrement atomicity**: for products with size/colour variants, `orderController.js` uses a single atomic conditional `$inc` (`updateOne` with a `$gte` stock guard) rather than a read-then-write, correctly preventing oversell races for that code path — the gap is scoped specifically to non-variant products (Finding 6).
- **CORS allowlisting**: `server.js` configures an explicit origin allowlist rather than a wildcard, appropriate for a credentialed API.
- **Secrets hygiene**: real `.env` files are gitignored; only placeholder `.env.example` files are tracked in the repo (Finding 54).
- **Mobile secure token storage**: `expo-secure-store` (Keychain/Keystore-backed) is used for the auth token, not plain AsyncStorage.
- **Escaping is correct in the majority of frontend render sites**: `cart.js`, `product.js`, `shop.js`, `wishlist.js`, and most of `main.js` consistently use `escapeHtml()`/`sanitizeUrl()` — the gaps (Findings 2, 29, 30) are exceptions against an otherwise-sound pattern, not the norm.
